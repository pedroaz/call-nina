# Call Nina

Local-first Electron app for Linux, macOS, and Windows for German learning: React/Vite renderer, validated preload/IPC, SQLite, and Codex App Server over STDIO. Use the supported Node/pnpm ranges in `package.json` and `toolchain.json`; `.node-version` and the recorded package-manager version are recommended bootstrap versions.

## Working agreement

- Every Codex CLI/Desktop session and agent, including small docs/skills and ad-hoc fixes, inspects branch, worktree and status read-only, maps the request to an existing approved task or proposes missing scope, then creates/selects its owned isolated task worktree before the first repository edit. Main may host the coordinator but is not an implementation scratch checkout; PR delivery belongs to the coordinator. Do not create duplicate tasks for an active task’s concerns; dirty-main transfer is recovery for existing changes, not the normal workflow.

- Keep work focused on the requested change, including small fixes needed to build or verify it; inspect current files and `git status --short`, and preserve concurrent work and learner data. Approved Ready issues authorize scoped commits, pushes, PR creation and merging through the coordinator. Release publication requires separate authorization.
- While the app is under development, do not add or retain compatibility paths solely for superseded app behavior, IPC/MCP inputs, or saved record formats. Use one current contract and update its callers and relevant skill instructions together. During development, explicitly versioned learning-format changes may reset incompatible learning data before current readers run. Retain valid profile/preferences, preserve unrelated files and credentials, and show a durable dismissible notice; never reset on corruption or an unknown newer schema. Keep the SQLite migration ledger.
- New task branches use `task/<issue>-<short-kebab-description>`; separate worker branches retain that issue number and add an ownership suffix. Authored task commits and PR titles use Conventional Commits (`feat`, `fix`, `docs`, `refactor`, `perf`, `build`, `ci`, `chore`, `style`, `revert`; optional scope and `!`). Each commit and PR body ends with `Refs: #<task>`; the body includes active `Closes #<task>` and the native parent epic URL when present. Product tasks require a native parent; an authorized existing bug labeled `bug` may be parentless. Preserve every distinct complete breaking footer in the PR body and squash message. The coordinator publishes linked branches and creates/edits/validates/merges PRs through `make github`; arbitrary UI/raw-gh metadata edits have no automatic refresh while hosted automation is disabled. Merge always revalidates current metadata.
- **No automated application tests.** Do not add or run unit/component/integration/E2E suites, saved test journeys, fixtures, mocks, coverage gates, or scheduled regression runs. Use the interactive Electron platform when verifying application behavior.
- **Exploration and major refactors may defer behavior verification.** Intermediate changes may leave the app incomplete, broken, or unable to build/run across tasks; do not restore functionality or launch the app after every edit solely to satisfy verification guidance. No repeated permission is needed to defer these checks. Report known breakage and unverified behavior, then perform a consolidated interactive verification round once the refactor is integrated, before declaring it working or release-ready. Explicit requests to verify still apply. Preserve learner data and security boundaries throughout; the existing `make check` policy remains unchanged.
- Interactive verification uses the real Codex connection and current learner data. Use GPT-6 Luna at its runtime default effort for AI verification, restore prior settings, and clean up only records created by the session through the UI. Do not substitute another model.
- **Local verification only for now.** Do not create, enable, or expand GitHub Actions workflows, hosted CI checks, deployment pipelines, or release automation until the user explicitly authorizes that work. Keep existing hosted pipelines disabled; run development verification locally. All code reviews are local only. GitHub metadata and branch protections are separate from CI/CD and do not authorize adding a pipeline. Agents must review the exact PR commit locally, fix actionable findings, run `make check` locally when preparing or updating a PR, and record the commit, results and any deferred interactive verification in the PR. Do not require a hosted `static` status check.
- Required delivery gates include independent exact-head local review and passing local `make check`. An unavailable gate blocks only dependent work: record the exact blocker, evidence, retained Run/PR, owner and resumption action without automatic blocker monitoring or repeated requests, and continue unrelated authorized runnable work. Nonblocking upstream bugs remain separately tracked.
- Use documented Make commands. Run `make check` only when static verification is requested or preparing a PR; it contains formatting, lint, and TypeScript checks, not tests. Do not run broad gates after every edit.
- Inspect relevant redacted logs before fixing bugs. Never log learner text, prompts, model output, credentials, raw protocols, or private paths. Signal processes only through exact lifecycle ownership.
- Keep skills focused on durable structural decisions, working preferences and implementation entry points. Current code, schemas and runtime observations establish what is implemented. Do not maintain reference documents inside skills, parallel implementation documentation, standalone runbooks or unsolicited progress/checklist files.

## Skills and sources of truth

Before new work and before a final response or detach, the coordinator reconciles Runs, Tasks, Dispatches, PRs, tracked/untracked primary changes and open bugs. Worker completion settles implementation, not delivery: continue all authorized runnable work through PR, required local gates, verified merge, task/Project/epic reconciliation and safe cleanup without asking the user to resume. Idle or long-running sessions, context limits and tool timeouts require receipt/liveness investigation, never assumed death/completion or duplicate dispatch. If a budget forces interruption, durably record exact state, owner, next action and resumption path in existing Run/recovery records; report incomplete delivery without promising unscheduled background work.

For approved GitHub work, one developer coordinator defaults to one implementer and one independent reviewer, with at most three workers and two isolated writers. Use an architect only for an unresolved design decision, never a routine architecture phase. The coordinator decides parallel issues or subtasks from dependencies and file ownership. Workers do not delegate recursively. GitHub owns product scope; Orca owns execution; Git owns integration. Product issues use exactly Epic → Task; smaller steps belong in checkboxes or Orca assignments. Use authenticated `gh` for every GitHub operation (`gh api` when needed), never a separate token, SDK or connector. Product planning follows interview → final epic/task proposal → explicit publication approval → GitHub creation; even Backlog planning issues wait for that approval. Only the Product Owner working with the user may make new scope Ready. Default delivery is merged into main with the actual merge commit and task closure verified; PR-only, app launch, deployment and release are distinct outcomes. Reconcile externally merged PRs without rerunning their old review gate. Reconcile task-related Orca workspace links/status with proven GitHub/Run state through supported operations, distinguishing active coordination from completed implementation; report unsupported links or sync explicitly. Close an epic autonomously only after every native child outcome, required delivery and epic acceptance criterion is verified; account for cancelled, duplicate and not-planned children explicitly. Keep incomplete epics open with remaining criteria. Keep recurring intake disabled until its activation prerequisites are proven and activation is explicitly authorized; use only the existing paused 15-minute `call-nina-ready-queue` heartbeat.

Intake inspects tracked and untracked dirty-main changes, preserves their original baseline/content, and transfers only explicitly owned approved hunks onto current origin/main task branches. Never blanket-stage or reset main. After verified merge, reconcile only proven unchanged transferred hunks and preserve concurrent or unrelated edits. Clean up completed agent-owned worktrees and local branches through documented Orca cleanup only after worker release, clean tracked/untracked state, no active task/verification/user ownership, and squash-aware proof all changes reached main; retain the primary checkout and uncertain work with reasons.

A dedicated worktree holds one fixed verification commit and the sole agent-owned desktop session. Other writers may continue elsewhere. No agent edits the verification checkout until cleanup and barrier release. Application behavior verification is not part of setup-only work.

## Discovered bugs and service configuration

Agents must capture evidenced bugs that are deferred or better handled separately as GitHub bug issues through `gh`, after searching for duplicates. Include the affected revision, expected/actual behavior, reproduction or source evidence, impact, relevant issue/PR, and why the fix is deferred or can run independently. Label unconfirmed suspicions clearly; never publish learner data or secrets. During an Orca Run, workers send the finding to the coordinator, who owns deduplication and issue creation; outside a Run the discovering agent may file it directly. Add new bugs to the Project as Backlog. Filing alone does not approve implementation. Intake also triages open bugs against evidence, duplicates and current main; failure to reproduce is inconclusive. The maintainer authorizes confirmed bounded fixes to intended existing behavior, with an explicit scope/disposition and Ready handoff; this does not authorize new product scope, destructive changes, services, releases or CI/CD. A local workaround does not close an unresolved upstream defect. The coordinator may parallelize an authorized fix with explicit ownership and dependencies; new scope waits for Product Owner agreement. Do not defer regressions introduced by the current change or acceptance blockers merely to merge sooner; fix them or mark the work Blocked. Security-sensitive reports must not expose exploit details or secrets in public issues; use the repository's private reporting route when available, otherwise alert the maintainer privately.

Prefer configuration as code for service integrations, including GitHub, Vercel and Clerk. Commit supported declarative settings and environment distinctions beside their owning code; use a maintained provider or an idempotent API/CLI reconciliation script when native config is insufficient. Make changes reviewable with a plan/diff before applying them, and validate resulting remote settings. Keep secret values and infrastructure state out of Git; document required secret names and their provision source. Document unavoidable dashboard-only steps alongside the owning integration. For Clerk, the maintainer creates the application/instances first; then use checked-in desired settings and supported APIs to reconcile configuration, with explicit instance selection and a diff before applying. Keep this desired configuration separate from user/membership data. Do not invent unsupported provider settings or provision services merely because this policy names them. Existing deployment/release authorization boundaries still apply.

## Code Review Rules

- Preserve learner data and existing on-disk formats unless an explicitly approved format change applies. Branding changes must not reset or silently relocate data. Report concrete loss or ownership risks.
- Keep renderer privileges narrow and runtime-validate IPC, AI, MCP and persistence boundaries. Report reachable trust-boundary violations and consequential contract mismatches.
- Preserve exact process and task ownership. Never infer completion from timeouts or kill unrelated processes. Review changed behavior and correctness; leave formatting and lint to static checks.
