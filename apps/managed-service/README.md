# Managed starter deployment boundary

This is a separate, disabled Vercel service project, not the public website. `desired.json` keeps preview and production disabled; the desktop package ships no endpoint or model. `make managed-service-plan` only compiles source and prints desired changes and parameterized budget-row SQL. It never deploys, provisions, reads secrets, applies SQL or calls inference. There is no scheduler or Git deployment automation.

The maintainer owns the separate authorization to choose/provision infrastructure, supply a service environment, approve a numerical operating budget and model cost evidence, permit non-Codex inference verification, and deploy/enable public access. Source/static delivery does not satisfy live acceptance for #82, #85, #92 or epic #76. #83 must display the starter as unavailable until an approved endpoint/model is shipped and acceptance establishes availability; no fallback to personal keys or another route is allowed.

## Reviewed configuration and secrets

After those approvals, replace only the intended environment in `desired.json` with a value accepted by `activeDeploymentSchema` in `deployment.ts`. Review the resulting diff and `make managed-service-plan` output before applying any remote changes. Pin the separate Vercel project/team, exact HTTPS origin, approval reference, direct Vercel ingress boundary, isolated Gateway funding, one allowed model/provider, time-limited cost evidence and numerical limits. Preview and production need separate database roles, budget epochs and Gateway credentials/funding; neither inherits the other. Local environments are always unavailable.

Required server-only secret names, supplied by the maintainer through the selected environment's secret store:

| Name                             | Provision source                                                                                                                   |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `NINA_STARTER_GATEWAY_API_KEY`   | Dedicated service-owned AI Gateway scope, never a learner key or ambient developer credential                                      |
| `NINA_STARTER_DATABASE_URL`      | Selected PostgreSQL primary's restricted service role; explicit database/user/password and verified TLS; no query-string overrides |
| `NINA_STARTER_THROTTLE_HMAC_KEY` | Maintainer-generated random 32-byte secret encoded as 64 lowercase hex characters; stable across instances                         |

`NINA_STARTER_ENABLED=true` is an additional explicit server switch. Vercel's `VERCEL`, `VERCEL_ENV` and `VERCEL_PROJECT_ID` must match the reviewed configuration; enable exposure of these [system variables](https://vercel.com/docs/environment-variables/system-environment-variables) in the separately approved project settings. The maintainer also sets the non-secret `NINA_STARTER_TEAM_ID` to the reviewed owning team ID; it is not an automatically supplied Vercel runtime variable. No secret values, linked-project state or database dumps belong in Git. The service imports no desktop credential storage and accepts no keys in its protocol. Never enable body logging, SDK telemetry, query-parameter logging or provider exception logging in the hosting/database/Gateway configuration.

Use a dedicated Gateway scope with **no cached BYOK credentials or automatic funding top-ups**. Gateway otherwise tries cached keys and may fall back to system credits ([documented behavior](https://vercel.com/docs/ai-gateway/authentication-and-byok/byok)); an API key alone does not prove isolated funding. Inspect that remote configuration under separate authorization before activation. The source pins one model/provider, disables SDK retries, sends no fallback models, and cannot override an incorrectly configured Gateway account. Do not enable a scope whose routing, billing ceiling or content logging cannot be verified.

Cost approval must bound **every billed component of one attempt** at the limits in `protocol.ts`: 256 KiB serialized Gateway request, 8192 total billed output/reasoning tokens, and any provider/Gateway overhead, minimum charge or internal attempts. Select only a model/provider whose enforced limits establish that bound; an ordinary output-token price or estimate is insufficient. Record authoritative cost evidence and expiry in the policy. The service reserves twice `maximumAttemptMicroUsd`; no invented monetary default is supplied. Hosting/database/request-flood costs are outside that inference ledger and require their own reviewed infrastructure spending limits before public activation.

## Durable control state

Review `packages/managed-generation/sql/001-budget.sql` and the generated plan. The source uses the maintained [Postgres.js driver](https://github.com/porsager/postgres) with parameter binding, verified TLS, restricted connection count, connection/statement/lock timeouts and suppressed notices. The schema stores only budget/control, random reservation identifiers, monetary charges, timestamps and rotating keyed network throttle hashes. It never stores a learner profile, input, prompt, response, IP address or personal credential.

Apply the SQL only to the separately selected primary under maintainer authorization. Use a dedicated owner role for migration; give the service role only schema USAGE and EXECUTE on `reserve`, `permit`, `settle`, never table writes or owner privileges. Inspect the inserted **disabled** budget row against the plan, including its policy digest, cost/time boundaries and all limits. Budget activation and remote settings readback are separate approved actions. No source path creates or enables a budget row. Before changing budget epochs, disable the old epoch and drain its admitted work; overlapping epochs each carry their own independently approved cap. Disable the durable row to stop admissions and subsequent repair attempts across all instances; disabling only an environment variable requires old instances to drain. Already admitted upstream work can still bill and stays reserved.

`reserve` locks the shared budget row and commits the worst-case two-attempt charge before inference. It atomically enforces the global spend cap, active leases, global admission rate and network rate across instances. `settle` refunds only attempts that were never dispatched. Timeout, cancellation, provider refusal and unknown usage retain the full attempted-call charge. Process loss or settlement/database failure retains the entire reservation; lease expiry releases concurrency but **never money**. Repeated reservation IDs are refused; results are not persisted or replayed. A new client retry is a fresh paid admission, never an automatic transport retry. Keep reservation IDs for the budget epoch; retire whole expired epochs only through separately approved accounting, never reset a live ledger. Row-lock behavior is defined by [PostgreSQL](https://www.postgresql.org/docs/current/explicit-locking.html).

## Native-client boundary and remaining verification

Only the Vercel entrypoint extracts `x-vercel-forwarded-for`, after matching server-owned environment/project/team and origin. [Vercel documents ingress overwrite and this header](https://vercel.com/docs/headers/request-headers#x-vercel-forwarded-for). Activation requires direct Vercel ingress, no custom trusted proxy configuration and no alternate origin bypass. Do not copy this header-based binding into a generic Node server or accept an identity field from the client. Confirm spoofed-header rejection against the real selected deployment before public acceptance.

Network throttling is abuse friction, not identity, per-person quota or native-client authentication: NATs share limits, address rotation can evade them, and fixed windows permit boundary bursts. CORS, an app-install identifier or a desktop-shipped secret cannot solve this. Global durable limits still cap admitted inference; external request-flood protection and hosting cost controls remain deployment prerequisites.

The single `POST /api/generate` endpoint accepts a strict structured learning input and the one approved model, runs the portable workflow plus at most one repair, and returns a validated result or bounded unavailable/shutdown/exhausted/throttled/conflict/cancelled/deadline/error response. Input/output bytes, overall deadlines, provider destinations and redirects are bounded. Client abort propagates through the request when the platform exposes disconnect; platform disconnect propagation needs live verification. Otherwise the server deadline stops further work, with conservative billing retention.

No inference, database connection, SQL execution, app launch, provisioning or deployment was performed for source delivery. The maintainer must authorize infrastructure and non-Codex verification; #85/#92 then verify actual SQL concurrency/restarts, native ingress spoofing, cancellation/deadlines, shutdown/exhaustion, provider price limits, secret isolation, shared workflow quality and deployment settings. Desktop main routes managed operations through `ManagedGenerationService` from `@call-nina/managed-generation/service`, including translation, explicit retry and cancellation. The static catalog never probes the endpoint; configured access is not live validation. Its default null configuration advertises no operations and fails unavailable; the adapter captures connection/root, retains submissions, supports explicit retries/cancellation, validates output locally and never reads a personal key.
