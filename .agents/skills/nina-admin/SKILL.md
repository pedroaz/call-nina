## Execute an operator request

Run `node scripts/admin/index.mjs help` from the repository root for operation names and arguments. Every operation requires `--environment preview|production` (or explicit `NINA_ENVIRONMENT`); help does not. Credentials come only from `.env.<environment>` plus explicit shell overrides, never the obsolete root `.env`. No arguments also returns discovery. Commands return one JSON document on stdout: `status` is `completed`, `review`, or `error`; completed/error responses contain `results`, errors include a sanitized `error`, and reviews contain `review`. Errors exit nonzero. Build/deployment diagnostics go to stderr.

1. Inspect only the prerequisites relevant to the request: credential presence, local infrastructure plan, and remote inspection when needed. Local database validation is not connectivity verification.
2. Invoke the requested mutation without `--yes` to prepare a non-mutating review. Some reviews read live state; builds may refresh generated output. Check the selected target and intended changes.
3. When the user's request already authorizes those changes, execute the same operation with `--yes`; do not ask again. Ask only for missing scope, an ambiguous target, or an additional action outside authorization. Deployment requires a deployment request. Existing validations still run during execution.
4. Inspect the structured result and available readback. Report completed and uncertain steps separately; never treat an unknown remote outcome as proof nothing changed. Do not blindly retry writes.

For `quota top-up USERNAME ACTIONS [GRANT_UUID]` and `users onboard USERNAME ACTIONS [GRANT_UUID]`, review generates a UUID when omitted. Supply that exact UUID for execution; `--yes` refuses grants without an explicit UUID. Retain it for every retry. If onboarding partially fails, inspect state and continue individual operations; never repeat onboarding or roll back a successful grant.

For account-creation requests, establish whether the account should have Nina AI access and, if yes, how many initial actions to grant. Ask together before creating the account when either choice is missing; reuse explicit answers already given. An explicit credentials-only request needs no extra question. Use `users create USERNAME` for credentials only, or `users onboard USERNAME ACTIONS GRANT_UUID` for creation, Plus assignment and the chosen allowance. Keep the CLI noninteractive: the agent asks the user, then supplies the selected operation and arguments. Never invent an allowance.

For an existing account's AI-enablement request, inspect `usage USERNAME` first. Assign Plus with `users set-tier USERNAME plus` when tier access is requested; use `users enable-ai` only to resume the text permission of an existing Plus account; preserve existing grants and only top up when an amount is specified. Hosted AI enablement and action balance are distinct from shared service activation. Check inference availability before claiming AI is usable. If the shared service is disabled, explain that account enablement alone cannot enable requests and establish the missing model, funding and spending limits through the hosted API workflow. Account creation must not silently activate the shared service or purchase funding. Report account access, remaining actions and service availability separately. Password reset is explicit and signs out other sessions.

Creation/reset returns the generated password in the operation result, including successful creation followed by onboarding failure. Display those login credentials in chat as requested by the maintainer. Do not persist them to repository files or copy them into logs. Provider keys, database passwords, and connection strings must never appear in chat or reports. If creation has an unknown outcome and no returned password, inspect the user before requesting an explicit reset; do not silently create again.

## Existing infrastructure and credentials

`scripts/admin/infrastructure.json` has explicit `preview` and `production` profiles selecting one combined Vercel project under `nina-labs-projects`, separate Clerk instances in application `app_3LQ6AdMzBg4yRCwYuK6qJcU2ylI`, exact canonical origins (`https://staging.callnina.de` and `https://callnina.de`), and separate restricted runtime roles. Preview and production use separate Neon databases. Reject mismatched environments; never fall back to production.

`infra project-setup` reviews creation/linking of the selected Vercel project and saves public IDs after identity verification. It connects no Git repository. `infra clerk-provision` reviews linking the matching Clerk instance, creating production only if absent, and saves instance keys directly to the private selected credential file. It never imports users. `infra domains-setup` assigns apex, www redirect and staging domains, and reports exact DNS records/ownership challenges. Registration stays at Squarespace. These operations require an explicit provisioning request; billing subscriptions and provider onboarding/consent remain maintainer actions.

Clerk authentication configuration uses the official CLI OAuth session: `npx clerk@4.1.0 auth login`. Never extract its token or substitute an instance secret for Platform authentication. CLI children receive no admin credentials. `infra clerk-link` can instead link explicitly supplied instance fields after Backend API identity/domain checks. `infra clerk-inspect` performs a Clerk-only live read; `infra clerk-apply` reviews a server-side configuration dry run before mutation. `clerk-policy.json` is the partial username/password, public signup, no-email, optional-organization policy. Preserve unrelated password protections. Full configuration stays in memory and compares desired leaves only. Platform paths require `/platform/`; validate schema changes with the exact app/instance IDs. Recheck config version before writes and never run concurrent configuration writers. Native API and origins are independently read back. Production allows the packaged renderer origin; Preview additionally allows the local renderer.

`infra plan` is local; `infra inspect` reads provider identities and the selected environment. `infra migrate`, `infra runtime-setup`, `infra apply`, `infra configure-client` and deployment are separate operations. Migrations verify supplied owner permissions and apply missing versioned SQL. Runtime setup generates and privately saves a distinct password before creating/reconciling the owned restricted role. Verify its ownership marker, absence of privileged role memberships/table access, and exact function grants on unpooled and pooled endpoints. Never upload owner credentials. Administration derives connection URLs in memory from the selected file's `PGHOST`, `PGHOST_UNPOOLED`, `PGUSER`, `PGDATABASE`, `PGPASSWORD` and `NINA_DATABASE_RUNTIME_PASSWORD`; never log those values.

`infra apply` verifies database credentials/permissions, reconciles Clerk origins, and uploads only allowlisted runtime credentials to the selected Vercel environment. It reads each encrypted value back and compares in memory. Text AI, speech and speech recovery remain disabled. Marketplace owner variables must not be connected to the application runtime. `infra configure-client` generates both public client profiles and the API environment map; it activates nothing. Packaging rejects incomplete/stale selected configuration.

Manually dispatched Deploy Vercel builds the combined artifact, verifies checksum/commit/run/environment/project identity, and uploads it without rebuilding. Supply pinned Vercel CLI 65.5.0 with `VERCEL_TOKEN` from the matching GitHub `Preview` or `Production` environment, only in the deploy job, never in arguments. Build jobs receive no credentials. Production requires main; Preview supports working branches and its staging alias alone receives a deployment-protection exception for native clients. Fresh projects require an initial production deployment before Preview. Preserve disabled automatic Git deployment. Desktop Release is separate and always uses production public configuration.

Retries inspect matching `ninaRun`, `ninaCommit`, `ninaVersion`, `ninaArtifact` and `ninaEnvironment` metadata before upload. Reuse only a verified ready matching deployment; inspect uncertain outcomes instead of blindly uploading again. Alias assignment/readback is separate and idempotent. A rollback selects a verified deployment in the same environment; it does not undo migrations. Never automatically roll back or rebuild under an existing release identity.

`credentials status` reports presence/source only. Generated credentials are saved atomically with mode 0600, preserving other entries. Provider keys, URLs and raw protocols never enter chat, logs or Git. Live provisioning and verification require the selected credentials; report missing inputs and unverified behavior honestly. One AI action covers admission and its repair; only zero-attempt requests refund it. Preserve normal budget/accounting invariants on routine operations; a separately requested destructive fresh reset is not an allowance renewal.

## Existing Marketplace database

Create Neon resources only under an explicit provisioning request. The maintainer completes Marketplace provider onboarding/consent. Use the matching `.env.preview` or `.env.production` PG values without logging host, database, username, password or connection strings. Connection URLs encode credentials and database names. The PostgreSQL adapter enforces verified TLS directly and rejects query-string TLS overrides. PGHOST_UNPOOLED owns migrations and administration; PGHOST owns runtime queries with `prepare:false` and single-statement function calls. Live pooled compatibility is checked only during explicitly requested runtime setup/apply.

`database-connect` is a local configuration check, not proof of connectivity or permissions. Admin migration/role batches use the dedicated unpooled admin connection with verified TLS, one connection, and the simple PostgreSQL protocol for parameter-free transactional batches. Parameterized reads remain parameterized; the pooled runtime adapter remains single-statement. `prepare:false` alone does not enable multi-statement batches. If a batch fails, inspect migration digests and object presence before retrying; never delete the ledger or recreate the database. Do not perform live permission checks when setup is deferred. Role setup and apply fail closed on privileged roles, role memberships, ownership, direct table/column/sequence grants, schema creation, or execution of internal Nina functions. PUBLIC/inherited privileges that cannot safely be removed without affecting others require administrator resolution; do not revoke shared privileges automatically. Apply validates the runtime credentials and effective privileges on both configured endpoints before uploading the URL, never falls back to the supplied owner, and keeps inference disabled. Migrations, grants, balances and existing resources are never reset.

`users enable-ai USERNAME` and `users disable-ai USERNAME` control the text permission of an existing Plus account, not tier assignment, Clerk identity or mobile sync. `usage` reports `hosted_ai_enabled` separately from remaining actions. Onboarding assigns Plus and grants the explicitly requested actions; a credentials-only user can use mobile sync without AI enablement. Apply the forward access/sync migrations and restricted grants before deploying clients using the new account contract.

## Separate speech allowance

The admin registry includes `speech enable USERNAME`, `speech disable USERNAME`, `speech usage USERNAME`, and `speech grant USERNAME CHARACTERS GRANT_UUID`. Mutations use the same review/`--yes` convention as AI allowances. A grant is append-only and idempotent by UUID; reuse its ID on retry. Granting characters does not enable speech or the global budget and never alters AI actions. Usage reports learner settlement states and conservative provider costs separately. Migration `005-speech.sql` and restricted runtime reconciliation are explicit prerequisites; no production change is implied by speech implementation.

`users set-tier USERNAME free|plus` changes both hosted service permissions without granting allowances and records the change. `users reset-beta [REVIEW_DIGEST]` is destructive and only for an explicitly requested beta reset: review binds exact Clerk user IDs and instance, execution requires the digest and drained work. It removes identities and synced libraries, retires balances with an audit entry, and preserves local data and global financial accounting. Never use it as part of ordinary deployment.
