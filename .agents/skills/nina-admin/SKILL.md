# Nina administration

Use this repository's `scripts/admin/` tools to carry out the requested operation. Work as the current agent; no separate agent service or MCP installation is needed. For runtime changes or accounting design, use [hosted API development](../call-nina-hosted-admin/SKILL.md). Preserve unrelated working-tree changes and learner data.

## Execute an operator request

Run `node scripts/admin/index.mjs help` from the repository root for operation names and arguments. No arguments also returns discovery. Commands return one JSON document on stdout: `status` is `completed`, `review`, or `error`; completed/error responses contain `results`, errors include a sanitized `error`, and reviews contain `review`. Errors exit nonzero. Build/deployment diagnostics go to stderr.

1. Inspect only the prerequisites relevant to the request: credential presence, local infrastructure plan, and remote inspection when needed. Local database validation is not connectivity verification.
2. Invoke the requested mutation without `--yes` to prepare a non-mutating review. Some reviews read live state; builds may refresh generated output. Check the selected target and intended changes.
3. When the user's request already authorizes those changes, execute the same operation with `--yes`; do not ask again. Ask only for missing scope, an ambiguous target, or an additional action outside authorization. Deployment requires a deployment request. Existing validations still run during execution.
4. Inspect the structured result and available readback. Report completed and uncertain steps separately; never treat an unknown remote outcome as proof nothing changed. Do not blindly retry writes.

For `quota top-up USERNAME ACTIONS [GRANT_UUID]` and `users onboard USERNAME ACTIONS [GRANT_UUID]`, review generates a UUID when omitted. Supply that exact UUID for execution; `--yes` refuses grants without an explicit UUID. Retain it for every retry. If onboarding partially fails, inspect state and continue individual operations; never repeat onboarding or roll back a successful grant.

For account-creation requests, establish whether the account should have Nina AI access and, if yes, how many initial actions to grant. Ask together before creating the account when either choice is missing; reuse explicit answers already given. An explicit credentials-only request needs no extra question. Use `users create USERNAME` for credentials only, or `users onboard USERNAME ACTIONS GRANT_UUID` for creation, Plus assignment and the chosen allowance. Keep the CLI noninteractive: the agent asks the user, then supplies the selected operation and arguments. Never invent an allowance.

For an existing account's AI-enablement request, inspect `usage USERNAME` first. Assign Plus with `users set-tier USERNAME plus` when tier access is requested; use `users enable-ai` only to resume the text permission of an existing Plus account; preserve existing grants and only top up when an amount is specified. Hosted AI enablement and action balance are distinct from shared service activation. Check inference availability before claiming AI is usable. If the shared service is disabled, explain that account enablement alone cannot enable requests and establish the missing model, funding and spending limits through the hosted API workflow. Account creation must not silently activate the shared service or purchase funding. Report account access, remaining actions and service availability separately. Password reset is explicit and signs out other sessions.

Creation/reset returns the generated password in the operation result, including successful creation followed by onboarding failure. Display those login credentials in chat as requested by the maintainer. Do not persist them to repository files or copy them into logs. Provider keys, database passwords, and connection strings must never appear in chat or reports. If creation has an unknown outcome and no returned password, inspect the user before requesting an explicit reset; do not silently create again.

## Existing infrastructure and credentials

`scripts/admin/infrastructure.json` selects the existing Clerk/Vercel resources and the restricted runtime role; adjacent `clerk-policy.json` records the required authentication policy and its Platform API configuration mapping. `node scripts/admin/index.mjs infra clerk-link` reads `CLERK_INSTANCE_ID`, `CLERK_ISSUER_URL` and `CLERK_PUBLISHABLE_KEY` from root `.env` (with shell overrides). It checks the instance identity and domains through the Backend API using `CLERK_SECRET_KEY`, checks the publishable key against the issuer, and saves only public local configuration after review. Linking never creates a Clerk application or instance; full instance configuration is a separate operation.

Use `infra clerk-inspect` for a Clerk-only live read, without builds, database or Vercel prerequisites. Full authentication configuration uses the [Clerk Platform API](https://clerk.com/docs/reference/platform-api). Prefer the official CLI session: the maintainer runs `npx clerk@4.1.0 auth login` once; `npx clerk@4.1.0 apps list` identifies the existing application. Set its `CLERK_APPLICATION_ID` in private root `.env`. Admin commands use the installed/cached CLI via `npx --no-install clerk@4.1.0 api --platform` with exact application and instance paths, not an implicit linked environment. CLI OAuth storage/refresh remains owned by Clerk; never extract its token. The instance Backend API `CLERK_SECRET_KEY` is not a Platform credential. CLI children receive no admin credentials. Do not ask the maintainer to obtain a separate Platform token when CLI login works.

`clerk-policy.json` contains the schema-confirmed partial patch for username/password, disabled email sign-in/collection, Open (`public`) access, and optional organization selection for personal Nina accounts. Unspecified password protections and unrelated instance settings are preserved. Use `npx clerk config schema --app APP_ID --instance INSTANCE_ID` when changing this mapping; never invent configuration fields or store credentials there. Administrator password recovery is Nina's `users reset-password` workflow. Apply refuses an absent mapping. Successful readback proves the configured mapping matches, not that an arbitrary replacement mapping covers all requirements.

Run `infra clerk-apply` for review and a server-side configuration dry run, then `infra clerk-apply --yes` when authorized. The command checks the application owns the linked instance, enables Native API when needed, reconciles renderer origins, and reads configured settings back. Full configuration stays in memory because Clerk's version depends on the selected field projection. Compare only desired leaves for partial patches, preserving unrelated protections. `clerk api --platform` still requires the `/platform/` endpoint prefix. Use `PATCH .../config?dry_run=true` for server validation; the CLI `config patch --dry-run` only prints a request. If a convenience command reports an expired session, check the same read through `clerk api --platform` before asking the user to log in again. CLI transport rechecks the version immediately before writing but cannot atomically enforce it because `clerk api` exposes no header option. Do not run concurrent Clerk configuration writers. The operation creates no instances/users and performs no deployment, database setup or key rotation. After a partial failure, inspect before retrying; confirmed steps appear in results. `infra clerk-inspect` owns full authentication-policy readback. `infra inspect` checks Backend API identity/origins only, so Vercel setup does not depend on a Clerk CLI session. `infra apply` remains the separate hosting operation and only reconciles Clerk origins. Provider account/instance creation, login/token issuance, billing consent and production DNS remain maintainer prerequisites.

`infra plan` is local and includes inference-policy/budget prerequisites. `infra inspect` reads remote state; `infra apply` reviews that comparison, validates target identities, reconciles settings and uploads only allowlisted production runtime secrets with inference disabled. It reads each uploaded value back and compares it in memory; never print decrypted values or treat variable-name presence as value verification. `infra database-connect` validates local PG parameters only. `infra database-check` connects read-only to check permissions; `infra migrate`, `infra runtime-setup`, `infra configure-client`, `infra apply` and `deploy` remain separate explicit operations. Configure-client generates validated public desktop/API settings; hosting packaging refuses stale generated settings. Manually dispatched GitHub Actions is the maintainer’s selected release/deployment route; see [release delivery policy](../call-nina-development/SKILL.md#release-delivery-policy). `make deploy prepare` remains a packaging primitive; `make deploy production` and the legacy admin `deploy` write path now return workflow instructions without uploading. The workflow implementation must land on main and pass CI before it is operational. Keep Vercel Git-triggered deployment disabled; CI must upload the combined artifact to the existing project. Deployment still requires an explicit deployment request; planning or preparing a workflow does not authorize publication. No operation activates inference automatically.

Credentials load from ignored root `.env`, with process environment overrides. `credentials status` reports presence/source only; edit provider credentials and Clerk connection fields in `.env` (see `.env.example`). Never pass credentials as arguments. Generated database credentials are written atomically with mode 0600, preserving unrelated entries. `credentials import` explicitly imports the old ignored secret file, rejects conflicts and preserves the original; there is no fallback. Builds receive no admin credentials. Hosting publication uses pinned Vercel CLI 65.5.0 with `VERCEL_TOKEN` supplied only to the deployment step from GitHub Actions secrets (prefer the Production environment; a repository secret is also supported). The CLI reads the token from its environment; do not pass it in arguments or copy a local CLI login session. Root `.env` remains for local administration, not CI. Project/team identifiers come from committed infrastructure configuration. Validate token compatibility and project identity; a bounded admin API token may not support CLI account lookup. Deploy Vercel builds only the combined website/API and then deploys its exact artifact through Production; Release desktop publishes desktop assets separately. Both retain the shared version and exact commit/run identity. Build jobs receive no production credentials; server/runtime secrets stay in Vercel.

The deployment job verifies the artifact checksum, commit/run identity, target, routes and function metadata, then uploads the already-built combined output. It does not rebuild, migrate, grant permissions or activate inference. A retry first reads matching Vercel deployment metadata and only reuses a ready production deployment with aliases assigned; uncertain or failed remote outcomes stop for inspection. For recovery, inspect the original workflow summary, Vercel deployment history and `ninaRun`/`ninaCommit`/`ninaVersion` metadata before retrying failed jobs. An explicitly requested rollback should select the previous verified production deployment in Vercel and use its rollback operation, then verify website/API behavior; it does not undo database migrations. Never automatically roll back or rebuild under an existing release identity.

Operator environment: `CLERK_SECRET_KEY` for the selected instance, `VERCEL_TOKEN`, and the existing Marketplace parameters `PGHOST`, `PGHOST_UNPOOLED`, `PGUSER`, `PGDATABASE`, `PGPASSWORD`. No direct Neon provider credential is needed. Owner/admin URLs are derived in memory from the unpooled host and supplied user/password; never persist a duplicate owner URL. Runtime URLs reuse PGHOST/PGDATABASE with the separate configured runtime role and generated `NINA_DATABASE_RUNTIME_PASSWORD`. Only the derived restricted URL is uploaded as `NINA_STARTER_DATABASE_URL`; stale local URL overrides are not consumed. Keep verified TLS and use URLs without query-string overrides. `migrate` checks the supplied role identity, primary status, schema creation, ledger access and ownership of existing Nina objects before applying missing versioned migrations. It never sets up roles. `runtime-setup` separately requires role-management authority, generates and privately persists a password before creating the restricted role, checks an ownership marker before reusing a role, and grants only schema USAGE and the current accounting and sync function signatures. Unknown existing roles are refused, not adopted. Never use the owner credential in Vercel.

One action covers an admitted request and its repair; only zero-attempt requests refund it. Explicit retries spend another action. Unknown/process-loss outcomes retain both reservations. `usage USERNAME` distinguishes conservative charges from reported Gateway costs; missing usage is unknown, not zero. Do not reset balances or active budget epochs on reruns.

Live provisioning/authenticated verification requires configured credentials. When deferred by the user, report it separately from successful local builds/packaging. Private distribution of the app and credentials does not imply public signup or downloads. Determine managed inference availability from current configuration and live readback; do not preserve a past activation status as a standing instruction.

## Existing Marketplace database

Never create a Neon account, project, branch or database. The maintainer owns Vercel Marketplace onboarding. Reuse root `.env` PG values without logging host, database, username, password or connection strings. Connection URLs encode credentials and database names. The PostgreSQL adapter enforces verified TLS directly and rejects query-string TLS overrides. PGHOST_UNPOOLED owns migrations and administration; PGHOST owns runtime queries with `prepare:false` and single-statement function calls. Live pooled compatibility is checked only during explicitly requested runtime setup/apply.

`database-connect` is a local configuration check, not proof of connectivity or permissions. Admin migration/role batches use the dedicated unpooled admin connection with verified TLS, one connection, and the simple PostgreSQL protocol for parameter-free transactional batches. Parameterized reads remain parameterized; the pooled runtime adapter remains single-statement. `prepare:false` alone does not enable multi-statement batches. If a batch fails, inspect migration digests and object presence before retrying; never delete the ledger or recreate the database. Do not perform live permission checks when setup is deferred. Role setup and apply fail closed on privileged roles, role memberships, ownership, direct table/column/sequence grants, schema creation, or execution of internal Nina functions. PUBLIC/inherited privileges that cannot safely be removed without affecting others require administrator resolution; do not revoke shared privileges automatically. Apply validates the runtime credentials and effective privileges on both configured endpoints before uploading the URL, never falls back to the supplied owner, and keeps inference disabled. Migrations, grants, balances and existing resources are never reset.

`users enable-ai USERNAME` and `users disable-ai USERNAME` control the text permission of an existing Plus account, not tier assignment, Clerk identity or mobile sync. `usage` reports `hosted_ai_enabled` separately from remaining actions. Onboarding assigns Plus and grants the explicitly requested actions; a credentials-only user can use mobile sync without AI enablement. Apply the forward access/sync migrations and restricted grants before deploying clients using the new account contract.

## Separate speech allowance

The admin registry includes `speech enable USERNAME`, `speech disable USERNAME`, `speech usage USERNAME`, and `speech grant USERNAME CHARACTERS GRANT_UUID`. Mutations use the same review/`--yes` convention as AI allowances. A grant is append-only and idempotent by UUID; reuse its ID on retry. Granting characters does not enable speech or the global budget and never alters AI actions. Usage reports learner settlement states and conservative provider costs separately. Migration `005-speech.sql` and restricted runtime reconciliation are explicit prerequisites; no production change is implied by speech implementation.

`users set-tier USERNAME free|plus` changes both hosted service permissions without granting allowances and records the change. `users reset-beta [REVIEW_DIGEST]` is destructive and only for an explicitly requested beta reset: review binds exact Clerk user IDs and instance, execution requires the digest and drained work. It removes identities and synced libraries, retires balances with an audit entry, and preserves local data and global financial accounting. Never use it as part of ordinary deployment.
