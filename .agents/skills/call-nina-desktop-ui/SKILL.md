# Call Nina desktop UI

Inspect the real renderer and current styles before changing a screen. Repository-relative starting points are `apps/desktop/src/renderer/App.tsx`, the affected feature component, `components/ui/`, `components/layout/`, `styles/tokens.css`, `styles/global.css`, and the locale resources under `locales/`. Follow hooks and contracts to establish behavior; no separate design inventory establishes what is implemented.

For visual design, layout, polish or UX changes, also use the available `impeccable:impeccable` skill and its relevant workflow. Resolve its location through the session skill catalog rather than a pinned plugin-cache path. Apply it within Call Nina’s existing visual language and shared components; it does not authorize replacing the app’s theme or overriding the user’s verification boundaries. Pure behavior fixes without presentation changes do not need a separate design workflow.

## Presentation ownership

- Make each changed surface feel like the other pages. Inspect a comparable existing page or dialog before choosing the composition; reuse its heading hierarchy, field widths, spacing, action placement and interaction conventions. Improve the affected flow without inventing a separate visual system for it.
- Keep related elements aligned at every supported width: headings, tabs and content share edges; labels and fields share columns; icons have consistent slots; row actions and dialog footers align predictably. Use shared layout tracks and tokens rather than one-off offsets. Long translations, wrapped labels and narrow layouts must retain deliberate alignment without clipping content.
- Browser controls own their density, icon slots, selection, focus and pending treatments. Desktop `activityPresentation.tsx` owns activity icon mapping; `PracticeComposer` owns the shared topic/chooser presentation. Feature components retain state and operations.
- Use `ContentRow` for activity/list presentation, shared table styles for tabular data, and `Section` for borderless groups. Do not remove Card borders/padding through descendant selectors to simulate a section.
- Use the shared type scale: page title 28/34 at 700; section 20/26 at 600; subsection 16/24 at 600; body/fields 16/24 at 400; controls/labels 14/20 at 600; supporting text 14/20 at 400; metadata 12/16 at 400; reading 18/28 at 400. Token source owns the values; the font-family assignments below distinguish Source Sans 3 controls from Source Serif 4 editorial headings. Fredoka is reserved for the wordmark.
- Use 20px control/navigation icons, 24px category icons in a stable 44px container, and 16px inline metadata icons. Category choices retain stable icon slots without colored badges and reserve checkmark space. Icon slots, not broad descendant SVG rules, own sizing.
- Comfortable controls are at least 44px high; compact controls are at least 36px with 14/20 field values. Icon buttons are square at the selected density. Use 4px metadata gaps, 8px label/icon gaps, 12px related-control gaps, 16px content gaps/compact padding, 24px sections/standard padding, and 32px page gutters (16px when narrow). Let long labels grow.
- Home, Practice, Learning path, Vocabulary and Mobile are top-level destinations, with Settings as a utility. Internal route IDs remain stable. Use one Page breadcrumb pattern and preserve the actual launch origin, draft guards and return context. Page widths are standard, form and reading; center each page within the available workspace, with its header, tabs and content sharing the same edges. Keep workspace gutters symmetric, including space reserved for the collapsed helper toggle.
- Keep ordinary controls flat. Use elevation for menus/popovers/dialogs. Use explicit primary, secondary, quiet and danger actions; place Cancel before the trailing confirmation in dialogs. Ordinary metadata uses normal case.
- Consolidate superseded CSS while migrating consumers. Base rules belong together, with state and container adaptations following them; avoid permanent appended override layers. Feature layouts respond to available workspace width, including an open helper.

## Durable design decisions

- Active learning surfaces use `components/activity/`: `ActivityWorkspace` composes Page; `ActivityFrame` owns adaptive reference/task panes, shared progress, feedback and footer. Wide workspaces with sufficient height scroll their content panes; narrow/short workspaces scroll naturally with a sticky footer. Use `RecallCard` for reveal presentation and `ActivityCompletion` for completion structure. Feature controller hooks retain saving, evaluation, reveal tracking and scheduling; presentation never infers completion. Keep layouts independent of launch route and preserve mounted drafts across responsive changes.

- Companion panels preserve the task's mounted content. At widths up to 80rem, navigation defaults to its compact rail and the helper opens only on request as an overlay; automatic Writing help is reserved for docked widths. Up to 68rem, expanded navigation overlays the rail instead of stacking above the task. Escape returns focus to the panel toggle; overlays must dismiss when they would cover a focused task control, including during resize. Keep these thresholds aligned in App and AppShell. At narrow widths (up to 52rem), page headers scroll naturally so sticky actions cannot collide with the fixed helper toggle.
- Filter interaction follows query complexity: simple catalog/library selects and search update directly; Saved results’ compound date/text form applies only on explicit submission. Provide a single reset for all criteria and preserve editing focus. Use the existing catalog for immediate browsing, Saved results FilterBar for submitted criteria, Settings for borderless form groups, ActivityFrame for tasks and ModalDialog for focused decisions as reference compositions.
- Learning references use semantic word/translation pairs with target-language attributes, reading-size target text, supporting translations and separators rather than a card per word. Shared ActivityCompletion may show a small Nina pose chosen explicitly by the feature: celebration for saved completion, listening for abandonment or empty review. The summary owns evidence/proficiency meaning; artwork never changes completion logic.

- The learning library browses declared paths: courses for multi-lesson sequences and scenarios for focused outcomes. Use authored titles, descriptions and levels; never derive them from IDs. Filter only the selected target language and keep progress/return context scoped to it. Search and type/level filters must remain usable as the catalog grows.

- Practice → Saved activities owns Activities and Results views. Results includes all saved learning records; activity buttons apply an explicit activity filter. Keep record details and mistake evidence in mounted dialogs, preserve return context and filters, and keep counts and filtering grounded in persisted activity references. History remains a storage concept, not a sidebar destination.

- Vocabulary uses Learning and All words tabs. Learning shows one review banner, visible recent word/meaning/source rows, and compact focus rows; All words retains search and management. Add content is the single guidance/text/image entry point. Open word evidence and focus editing in dialogs, not accordion stacks. Use “Recently added” for additions without implying mastery, and compact addition feedback beside navigation. Keep source labels grounded in saved provenance.

- Learning path uses library → trail → lesson → activity navigation. Progress belongs to its trail or lesson; checkpoints remain authored trail stops. Review is a separate explicitly scoped destination with a preserved return context. Activity feedback stays visible until the learner chooses the next step; only saved completion unlocks continuation, including Voice returns. Browsing never marks work started, and skipped work never counts as completed or mastered.

- Keep a calm, warm, light-only studio style: cream surfaces, espresso text, terracotta actions and peach selection. Use semantic feedback colors only for actual learning/status meaning. Use locally bundled Source Sans 3 for desktop interface text and functional headings, with Source Serif 4 for page/section titles, catalog and library entry titles, dialog titles, recall prompts and reading passages. Keep field labels, navigation, metadata and utility subheadings in Source Sans 3. Reserve Fredoka for the brand. Keep the warm workbook direction: paper surfaces, quieter unselected activity choices, and unfilled category icon slots; use pale clay selectively for selection. Prefer compact rows and clear section hierarchy over nested cards or repeated headings. Hide detail only when it improves the task flow. Preserve full learner content and essential task instructions.
- Use rounded Lucide icons consistently (20px controls/navigation, 24px activity choices). Keep labels on important actions. The locally bundled cartoon Nina is an adult Rhodesian Ridgeback wearing a headset; use the generic welcome/listening/thinking/celebration poses sparingly. Never require topic-specific artwork or runtime image generation for learner-created activities.
- Use the shared Page header and refresh slot across screens, Tabs for sibling views, and Breadcrumbs for nested activities with their actual parent destination. Refresh data without remounting drafts or active exercises. Keep language switching in the left sidebar and one compact, accessibly labeled helper toggle at the app shell’s fixed top-right edge, without a full-height rail. Keep its position stable when the helper opens or closes; page and helper headers do not duplicate it.
- Semantic colors, type, spacing, radii, borders, shadows and motion come from `packages/design-system/src/index.ts`; use `make generate design-tokens` to regenerate browser CSS. Import its `tokens.css` and local `fonts.css` before desktop `styles/tokens.css`, which owns only desktop metrics and aliases for existing renderer sizing. Use accessible text aliases on brand and state surfaces.
- Shared browser controls live in `packages/browser-ui/src/` and remain independent of Electron, routing and feature state; desktop `components/ui/` re-exports them beside app-specific controls. Use explicit density/semantic variants, React Aria, CSS Modules, shared tokens, Lucide and i18next/react-i18next. Screens own layout and state; extend the shared controls before introducing alternatives.
- Let page/card/field/action layouts own spacing. Use shared spacing tokens and explicit `gap` on every multi-item flex or grid container; do not rely on adjoining borders, incidental margins, or whitespace in JSX. Give controls inside bordered cards and compound rows a visible internal gutter from the container edge and from sibling controls. Edge-to-edge joins are reserved for intentional structures such as table cells, tab indicators, and disclosure dividers. Check destructive and trailing actions especially, including long translated labels and narrow layouts. Adapt to available workspace width; inspect existing breakpoints in CSS. Never conceal layout defects by clipping overflow. Keep long content and enlarged text reachable.
- Use concise labels. Use InfoHint for optional explanations while keeping essential instructions, privacy information and destructive consequences visible. Keep Cancel beside the initiating action or progress.
- Choose visible sections, expandables or dialogs by the task and comparable app flows; none is the default for every optional setting. Keep frequently used controls and information needed for comparison visible. Use an inline expandable for a short, secondary detail that benefits from remaining beside its context. Use a shared ModalDialog window for a bounded configuration or inspection task that needs focused space while preserving the underlying page. Avoid long forms appearing far below their trigger, accordion stacks and dialogs that only add a step before navigation. Small popovers suit brief contextual utilities; direct destinations should navigate directly.
- Keep active values, pending operations, actionable failures and uncertainty visible without expansion. Retain deliberate answer/transcript reveals for recall. Dialogs have a clear title, consistent grouped actions, a reachable Close control, Escape/outside-click dismissal and focus restoration. Preserve drafts when dismissal is merely closing a view; do not silently discard edits or make dismissal appear broken.
- Substantial writing comparison, completion answer review, saved result and mistake evidence use the shared large ModalDialog with a dimmed backdrop, persistent localized Close action, Escape dismissal and a scrolling body. Keep the owning screen, draft, selection, filters and activity controller mounted. Result dialogs use keepMounted so nested translations and pending operations survive closing. Modal navigation never creates attempts, regenerates content or records support use.
- The active-exercise Lesson guide uses the same large modal, opened by a secondary book-icon button in the activity header. ActivityHeaderActionsContext supplies route-owned actions consistently across exercise, flashcard and prepared-activity workspaces. The lesson-page guide tab retains Overview, Explanation and Vocabulary sections; avoid nested accordion stacks.
- Ctrl+G remains exclusively the existing chat helper. Do not add reference sidebars, floating reference windows or notes/chat tabs. Keep required passages with the task, preserve saved translation state across hiding, and keep lesson Explanation/Examples mutually exclusive within their inline-help group. Verify these treatments at wide and narrow workspace widths with the helper both open and closed.
- Keep every registered interface locale complete, including keys and interpolation placeholders. Interface, learning and explanation languages are independent; use shared language definitions and explicit capabilities. Preserve substantive learning text and learner input on failure.
- Keep provider connection optional in local onboarding. AI entry points name the required operation and explain unavailable access while retaining local input and prepared practice; never imply a provider subscription is a Nina plan.
- Preserve accessible names, roles, keyboard operation, focus restoration, selected/disabled/pending/error states and reduced motion. Icon-only secondary actions need names and tooltips; important actions need text. Meaning cannot depend only on color.
- Passive programmatic focus destinations (revealed answers, helper containers, status regions) use `data-focus-anchor` to avoid drawing a control outline around reading content. Headings and table captions with `tabIndex={-1}` follow the same global rule. Preserve their focus behavior for assistive technology; keep visible keyboard focus on actual controls and keyboard-scrollable panes. Do not highlight an entire containing card merely because a descendant is focused.
- Keep participation, skipped work and proficiency evidence distinct. Explanations and corrections must remain understandable without exposing internal implementation details.

CSS-module declarations use `scripts/build/generate-css-types.mjs`, called by the desktop and browser-ui build wrappers; inspect the owning build/dev scripts and regenerate after class changes. Do not weaken TypeScript checks.

Follow the development skill’s exploration/refactor deferral policy; intermediate screens need not work or be visually verified after every change. Use the running development app for visual and behavior checks under the Electron skill; no separate owned session is required. If the user explicitly takes ownership of verification, leave all requested checks and app interaction to them and report unverified behavior. Otherwise, for behavior verification, use [interactive Electron verification](../call-nina-electron-verification/SKILL.md) to inspect changed screens, including keyboard/focus and relevant states. Scale language coverage to the change: for small, localized UI changes, check the user’s current interface language at the normal width and one other supported language with longer translated labels at a narrow width. Reserve checks across every supported interface language at normal and narrow widths for larger changes, such as broad screen redesigns or shared layout/navigation changes. Choose the longer translation based on the affected labels, and restore the original interface language when useful or requested. Generation uses real GPT-6 Luna; local layout checks need no model call. Report observed behavior and unexercised states. No automated UI tests, screenshot suites or stored journeys.

Provider setup currently uses a focused dialog with in-memory edits retained when dismissed and reopened. Keep its sections and actions consistent with other app dialogs. Choose visible or expandable secondary details using the task criteria above rather than a provider-specific blanket rule. The sidebar links directly to Settings without a popover.

AI providers settings owns capability defaults and advanced learning-action assignments. Provider inspection never changes routing. Exercises show the resolved provider/model beside each AI function without selection controls; the sidebar summarizes routing and links to Settings. Distinguish configured credentials, account access, supported operations/model modalities, and actual execution evidence.

Mobile follows Vocabulary and owns explicit snapshot publishing, independently of AI provider settings. Shared flashcard messages live in `packages/learning-ui`; desktop and native players reuse them while keeping platform-specific controls. Native interface and editorial font aliases map to the same Source Sans 3 and Source Serif 4 assets as desktop.
