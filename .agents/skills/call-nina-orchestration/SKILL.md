# Autonomous development

GitHub owns product scope, Orca owns execution, and Git owns integration. Read root/scoped rules and relevant development skills. All GitHub operations use authenticated `gh`; use `gh api` for gaps. Settings are explicit in `development.json`. Never use separate token configuration, a GitHub SDK or connector.

## Pick up and coordinate

Before new work and before any final response or detach, reconcile existing Runs, Tasks, Dispatches and receipts with issue/PR state, tracked/untracked primary changes and open bugs. Account for each authorized task's delivered stage, remaining runnable action or evidenced blocker and owner. Use existing Run/recovery records, not a parallel checklist. Worker completion is implementation settlement, not delivery; continue authorized runnable work through the delivery steps below without asking the user to resume. A blocker stops only dependent work; separately track nonblocking upstream bugs and continue independent approved work.

Use `make github ARGS=queue` to inspect approved Ready work and existing claims, and read open bug issues through `gh` even when they are Backlog. The sole scheduler is the existing Codex heartbeat `call-nina-ready-queue`, paused at 15-minute intervals and targeting the current coordinating conversation; `development.json` keeps `intake.enabled=false`. Do not create a scheduler or enable either switch during preparation.

Before activation, verify the workflow is published, Project read/write permissions work, supervised startup proves exact terminal/Run ownership and duplicate prevention, and independent local review and static checks are available. Reconcile existing Runs, claims, Dispatches and PRs first. Prove one bounded intake decision: if disabled, stop without launch; if the existing coordinator is actively working, do not interrupt it or duplicate assignments; if that owner is proven idle and approved work is actionable, send one bounded resume through the documented Orca handoff and retain its delivery receipt, never create another coordinator. Otherwise use the documented startup path only once ownership and activation are proven. An uncertain or unavailable owner is a blocker, not permission to replace it. Stay quiet without actionable change. Report remaining prerequisites and activation steps: explicit authorization, enable both existing switches, then observe a real wake-up using the intended conversation and single owner. Configuration alone does not prove unattended intake works.

Read `make orchestrate ARGS=help` and the installed Orca CLI orchestration skill. Use the explicit resolved IDE executable; Linux `/usr/bin/orca` is unrelated. Read version-matched receipt/recovery guidance rather than retaining a command manual here. Bind the Run using its proven coordinator handle. After interruption, reconcile Run/Task/Dispatch and GitHub issue/PR state before any launch. Unknown outcomes never authorize duplicate dispatch.

`make orchestrate` opens an Orca-managed Codex terminal from outside Orca, or returns the role instructions to the exact invoking managed Codex terminal inside Orca. Use Orca's bare `codex` launcher; appended arguments do not establish managed launch authority. Keep project model/effort defaults aligned with the coordinator role and verify effective settings before Run mutation or dispatch. `--idle` still delivers the role policy, then waits for user work without creating/binding a Run or claiming tasks. Bind only from the owning terminal with its own launch identity and authenticated current Run; never synthesize or copy credentials or select a sibling by focus.

Startup and binding share the repository operation lock. An existing binding, coordinator candidate in complete repository terminal inventory, unresolved Run owner, or retained startup attempt blocks another coordinator. Historical Runs may be skipped only with positive owner-exit, settled-task and released-resource evidence, or a proven different Git repository. Keep creation, readiness and delivery receipts under the shared orchestration state, including failed or uncertain calls. Input acceptance does not prove a started turn; pending/rejected/unknown delivery requires inspection of that exact terminal and receipt, never blind resend or relaunch. For recovery, inspect the exact Run/terminal and saved attempt, confirm owner exit and Task/Dispatch settlement through the installed CLI, then archive the reconciled startup marker while retaining its receipts; a remaining binding must be finished by its owner. A stale Run handle whose scope or exit cannot be proven remains blocked for operator investigation; do not reset the Run or infer exit from absence or timeout. Do not remove another operation's lock or auto-rebind a changed generation.

Default to one implementer and one independent reviewer for a bounded task. Use an architect only for a concrete unresolved design decision; do not add an architecture phase routinely. The coordinator decides parallel issues or subtasks by actual interface dependencies and ownership. At most three workers and two writers. Every assignment names the outcome, owned paths, exclusions, dependencies, relevant skills and acceptance evidence. Role files own model/effort; the launcher verifies effective settings. Workers never create workers. Inconclusive explorer results return to the coordinator; use the architect once only if a design decision remains, then report a concrete blocker.

Use Orca's structured agent mode for local workers. Verify the returned launch mode and any fallback reason alongside effective model/effort, retain the receipt, and operate workers through Dispatch-based orchestration commands; a structured worker handle is not a terminal. Keep the coordinator's interactive terminal separate from the worker mode preference.

## Discovered bugs

Follow the root bug policy. Workers report findings through Orca; the coordinator searches GitHub before creating one bug issue, adds it to the configured Project as Backlog, and returns the issue link to the worker and originating task. Use `.github/ISSUE_TEMPLATE/bug.yml` as the issue-body guide when authoring through `gh`. Record whether it blocks acceptance and whether its owned files/contracts permit independent work. Intake reproduces or inspects evidence for open bugs against current main and duplicates and records each disposition. Failure to reproduce alone is inconclusive. Under the maintainer authorization, confirmed bounded fixes to intended existing behavior may be scoped, made Ready and assigned separately in the current Run; honor dependencies and writer limits. New product scope, destructive work, service integrations, releases and CI/CD still require separate agreement. Only close a bug with evidence it is fixed, duplicate or invalid; a local workaround leaves an unresolved upstream defect open. Existing bugs labeled `bug` may have no native parent; the label classifies the issue, while maintainer authorization and the Ready/claim workflow still govern execution. Product tasks retain native Epic → Task parentage. If filing fails, retain the finding in the Run and report the failure; do not claim an issue exists.

## Branches and integration

Before any repository edit, every agent and Codex CLI/Desktop session (including small docs/skills and ad-hoc fixes) inspects branch, worktree and status read-only, maps to an existing approved task or proposes missing scope, and selects/creates its owned isolated task worktree. Main may host the coordinator but never scratch implementation; the coordinator owns PR delivery. Reuse active tasks for covered concerns; the dirty-main procedure below is recovery, not the default editing path.

Inspect both tracked and untracked changes in the primary/main checkout at intake, alongside existing tasks and PRs. Preserve the original baseline SHA and exact content/diff outside the task commit, map coherent approved hunks to explicit owners and existing tasks, and propose only missing product scope. Transfer only those hunks into isolated task worktrees from current origin/main, resolving against that baseline without overwriting unrelated committed changes. Never blanket-stage, reset, discard or automatically commit dirty main.

Create separate Orca writer worktrees from an explicit committed baseline. Run `make setup` per new worktree; do not share dependencies, output or runtime data. Writer assignments include numeric `issue` and exact `branch`; task creation and launch enforce `task/<issue>-<description>` and the assigned checkout branch. The launch guard rejects the primary and coordinator checkouts; it does not intercept editor writes or replace every session's pre-edit inspection. Separate writer branches add an ownership suffix. Workers commit scoped changes with Conventional Commit headers and `Refs: #<task>` footers, and never push or merge.

The coordinator alone integrates settled worker commits with normal Git. GitHub claim, publication, metadata status, evidence and merge commands require `--run` and live caller ownership: authenticated Orca `run-current` without `--from`, the invoking launch handle, and the live Run handle/generation must match the binding. Never copy or synthesize another session's identity or credentials. A clean linked integration checkout may differ from the bound integration root when both share the same Git common repository. Check changed paths against assignments, inspect conflicts and preserve concurrent edits. Freeze only the verification checkout, never all unrelated writers. Keep worktrees until their commits are accounted for. Do not reset, clean or force-delete as recovery.

Process entire Orca message deliveries before acknowledging them. Reply to questions, validate completion against the active Dispatch and release only settled owned workers through Orca. For idle or long-running sessions, context interruptions and tool timeouts, inspect exact receipts, Task/Dispatch state and layered worker/terminal liveness using the installed recovery guidance. Elapsed time, silence or an accepted input alone proves neither death nor completion; never duplicate dispatch or retry an uncertain mutation blindly. Continue independent runnable work while resolving the affected ownership.

If a context or execution budget forces interruption, preserve exact Run/Task/Dispatch IDs, branch/HEAD, PR and gate state, worker/resource ownership, pending receipts, blocker, next action and concrete resumption path durably in existing Run/recovery records outside any checkout slated for removal. Identify the continuing owner and report delivery as incomplete. Do not claim a handoff was accepted without a receipt or promise background work without an authorized scheduled mechanism; do not enable intake to manufacture one.

## Review and merge

Run independent local review on the integrated commit using applicable Code Review Rules. Reviewer and verifier assignments require an explicit `commit`; launch them at that same baseline. Include the reviewed SHA in completion evidence. Corrections require a new review task bound to the corrected commit; never reuse a completed review to attest another SHA. Route findings to an implementation owner. Prepare and update PRs with local `make check` (static only), acceptance evidence and explicit verification limitations. Record passing local static results with `--static-check-commit` set to the reviewed PR head. Do not create, enable or expand CI/CD workflows, hosted checks, deployment pipelines or release automation without explicit user authorization. All code reviews and verification are local only.

For behavior changes, reserve a clean dedicated verification worktree at the integrated commit using `verify-enter`. The verifier uses interactive Electron controls and application Luna at runtime-default effort. No automated application tests or saved journeys. Stop the session and inspect cleanup before the coordinator calls `verify-leave`. Preserve earlier recovery journals; setup-only work does not launch the app.

Use `make github ARGS="publish --run RUN --issue N --branch task/N-description --baseline SHA"` from the clean integration branch. It creates/verifies the native issue development link using that explicit baseline and pushes local HEAD without force; an existing unlinked remote branch is a conflict. Opening a PR replaces the branch link with a PR connection.

Use `make github ARGS="create --run RUN --branch task/N-description --title-file PATH --body-file PATH"` and `edit --run RUN --pr N --title-file PATH --body-file PATH` for controlled metadata writes. Titles follow Conventional Commits; bodies include active `Closes #N`, the native parent epic URL when present (required for product tasks), `Refs: #N`, and all distinct complete source breaking footers. Only the task may be closed by keywords anywhere in the raw outgoing squash title/body, including colon syntax and Markdown examples or comments. `validate --pr N` is read-only; adding `--run RUN` refreshes the required `nina/task-metadata` status. Controlled writes invalidate and reread server metadata. Arbitrary UI/raw-gh edits cannot automatically refresh status under the local-only policy; status alone never proves the current title/body. `merge --run RUN --pr N` always validates a fresh snapshot, rereads it, supplies the exact squash subject/body and checks the actual squash message (allowing only GitHub’s exact PR-number subject suffix), resulting task closure and unchanged open parent epic when present. GitHub protects the head SHA atomically but offers no title/body compare-and-swap; observed concurrent changes block merging.

`make pipeline-policy` shows the exact additive desired-settings diff and digest. After reviewing it, `make pipeline-policy ARGS="apply --plan-digest SHA"` rereads for drift and verifies readback. It owns only paused Actions, PR-title/body squash defaults and the dedicated main-only `nina-task-metadata` ruleset; unrelated protections/checks/reviews remain intact. No hosted static check is added.

Record independent exact-head local review and verification evidence using the GitHub helper (`--verification-commit` must match the review assignment and PR head). Resolve actionable findings, locally re-review corrections at the new commit and repeat only affected verification. If a required local gate is unavailable, record and report the exact unmet gate, evidence, retained Run/PR, owner and concrete resumption action. Stop only dependent work, without automatic blocker monitoring or repeated requests; continue unrelated authorized runnable work. Use the helper merge command to check exact-head local evidence, recorded passing local static checks, current task metadata and resolved discussions before squash merging. Treat release publication separately.

## Delivery, reconciliation and cleanup

Default delivery is merged into main with the actual merge commit and task closure verified. Honor an explicit PR-only target. Application launch, deployment and release are distinct outcomes with their own scope and authorization. Report the achieved stage accurately. If a maintainer externally merged a PR, verify its actual merge commit on main, delivered scope and task closure, then sync Project statuses and remove obsolete dependency blockers; do not rerun the old PR review gate or claim it passed. Report any delivery mismatch explicitly.

Reconcile task-related Orca workspace links and status against verified GitHub/Run outcomes using the installed supported `worktree set` operations and read back the result. Retained delivered worktrees should show completed implementation; an active coordinator workspace may remain active even when an associated task is Done. Inspect CLI/API support for issue/PR links, report unsupported fields explicitly, and do not promise automatic bidirectional sync or add a sync service.

Update task status through the Project helper. Enumerate every native child of an epic, including closed children; verify their outcomes, required merged deliveries and the epic acceptance criteria before closing it autonomously. Cancelled, duplicate or not-planned children require an explicit disposition accounting for the intended outcome, not just a closed status. Keep incomplete epics open with concrete remaining criteria. Follow-up product scope stays Backlog until agreed with the Product Owner.

After verified delivery, compare the preserved dirty-main baseline/content with the delivered changes and fresh tracked/untracked state. Reconcile only transferred hunks that are proven unchanged since intake and actually delivered, retaining all concurrent/unrelated edits. For an untracked file, remove or reconcile it only when its entire unchanged content was transferred and delivered. If overlapping edits or changed main make attribution uncertain, retain the hunk/file and report why; never restore a whole file just to remove one delivered hunk.

Automatically clean up completed agent-owned task worktrees/local branches only after all owned workers are settled and released, no active task, verification barrier or user session owns the checkout, and both tracked and untracked state are clean. Prove all branch changes reached main using the reviewed PR head, actual merge commit and baseline-aware diff/content comparison; squash merges need this evidence because ancestry alone can fail. Closed issue status or one merged PR is insufficient if additional changes exist.

Read the installed `orca worktree rm --help` and Orca cleanup guidance, then use normal `orca worktree rm --worktree <exact-selector>` from a retained checkout. It attempts local branch deletion but retains pre-existing or not-provably-merged branches; inspect the receipt and report retained branches instead of forcing deletion to bypass squash uncertainty. Preserve the primary checkout, user-owned sessions, undelivered work and uncertain worktrees with explicit retention reasons. Do not use blanket deletion, `--force` or failed-hook overrides. Before a final response or `finish`, repeat the cross-system reconciliation above; continue every authorized runnable delivery action unless the user stops work or a budget forces the durable handoff described above. Task/Dispatch settlement and the helper's worker/barrier checks alone do not establish delivery. Detach only after resource accounting and verified delivery or a durable blocked/budget handoff with owner and resumption path; unresolved ownership remains retained. Keep recovery receipts outside any checkout being removed.
