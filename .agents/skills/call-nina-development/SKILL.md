# Call Nina development

Work directly with the user as one agent. Read root and scoped `AGENTS.md`, inspect branch, worktrees and tracked/untracked status, and preserve concurrent source work. Development app data is disposable under root `AGENTS.md`. A chat request or optional ticket supplies scope; no task status or external execution record is required. Use the user's model selection and ordinary Git isolation when useful. Current code and runtime observations establish implemented behavior.

## Find the owner

Paths below are relative to the repository root. Follow imports and callers rather than assuming a file is the whole feature.

- Commands and supported toolchain ranges: `Makefile`, `package.json`, `.node-version`, `toolchain.json`; lifecycle and logs: `scripts/dev/lifecycle.mjs`, `scripts/dev/lib/lifecycle.mjs`, `scripts/dev/lib/log-view.mjs`.
- Incremental builds: application TypeScript output and build metadata live under each app’s `build/`; Vite owns runtime bundles under `dist/`. Shared packages emit to their own `dist/`. Keep these owners separate and reserve cache removal for `make clean`, rather than forcing recompilation on ordinary starts.
- Desktop wiring: `apps/desktop/src/main/backend.ts` and its internal `services/` owners, `apps/desktop/src/preload/`, `apps/desktop/src/renderer/App.tsx` and the affected renderer component.
- Shared design values: `packages/design-system/src/index.ts` exports browser and native representations; regenerate browser CSS with `make generate design-tokens`. Local font CSS, binaries, brand art and license files live in the same package. Keep the source dependency-free; desktop metrics stay in the renderer.
- Shared browser controls: `packages/browser-ui/src/`, consumed by desktop and website. Desktop activity presentation, composer state, navigation, content rows and table layouts live in the renderer. Keep this React/CSS layer separate from portable design tokens and native components; it must not import desktop services, routing or feature state.
- Shared contracts: `packages/contracts/src/`; portable generation context, prompts, validation and bounded repair: `packages/learning-workflows/src/`; deterministic learner rules and runtime validation: `packages/domain/src/`.
- Storage: `packages/persistence/src/repository.ts` is the public façade; `repository-{settings,vocabulary,activities,exercises,history}.ts` own internal operations and `repository-support.ts` owns shared schemas/helpers. Storage also includes `migrations.ts`, `sqlite.ts`, `data-root-layout.ts`, `data-root-selection.ts`, and the feature's persistence module.
- Course format and loading: `packages/contracts/src/learning-path.ts`, `packages/persistence/src/learning-path.ts`; authored multilingual catalog: `content/curriculum/catalog.json` and `courses/<language>/` beneath that directory; topic inventory and validation: `content/curriculum/` and `packages/domain/src/curriculum.ts`.
- Per-user install/update/removal: `install/`; platform filesystem ownership: `packages/platform/src/`. Keep install ownership separate from learner-root ownership.
- Packaging: `apps/desktop/electron-builder.yml`, `scripts/build/build-mcp-helper.mjs`; integrations: use [the Codex integration skill](../call-nina-codex-integration/SKILL.md).

## Structural decisions

- Electron main owns filesystem, processes, SQLite and provider transports; renderer stays browser-only behind narrow validated preload/IPC. Desktop and independently launched STDIO MCP reuse shared contracts, domain and persistence.
- SQLite owns mutable private learner state. Reusable curriculum is repository product data packaged read-only. Keep learner files, credentials and research scratch material out of Git. The selected data root is portable; no automatic backups or folder-copy workflow. Repository installs update only through the explicit installer command; there is no background updater.
- One configuration per AI provider, its model preference, and capability/action routing defaults belong to the portable learner root, independently of language profiles. Device config owns platform-encrypted keys; portable metadata contains only opaque references. Learning cleanup and exports never include key material or reset connection choices. Root switches preserve both roots; connection removal never removes learner records or provider authentication.
- Runtime-validate AI, IPC, MCP and persisted inputs. Preserve data-root generations, leases, idempotency and transactional migrations. Use one current contract; follow the learning-format policy below.
- Local onboarding and supported prepared practice depend on the learner data root, not provider authentication. Keep local learner identity, provider accounts/credentials and device capabilities separate; a provider plan confers no Nina entitlement.
- Keep learning activities self-paced and distinguish participation from skill evidence. Voice stays in Codex; Call Nina stores bounded structured results, not audio or transcripts. Model capabilities come from the connected runtime.
- Preserve imported material text through renderer, generation and storage boundaries; whitespace validation must not rewrite the source. Attempts retain their exact content/material revisions, while later feedback appends evidence without replacing the original answer or evaluation. Reusable material lifetime is separate from activity lifetime: deletion may remove explicitly owned inline material only when no edited revision or surviving reference needs it. Never infer ownership for existing material or collect unrelated orphans.

## Data and process boundaries

Keep Electron context isolation and sandboxing enabled, Node integration disabled, and never use `remote`. Main validates privileged IPC senders, denies unexpected renderer permissions/navigation, and opens only validated external/handoff URLs. Contracts perform no I/O; domain stays deterministic and browser-compatible; persistence owns SQLite and migrations; platform owns OS primitives. Define contracts before extending adapters, and preserve the dependency direction enforced by ESLint.

Do not add compatibility paths solely for superseded behavior, inputs or formats. Only explicitly approved versioned learning-format changes may reset incompatible learning data before current readers run. Preserve valid profile/preferences, credentials and unrelated files; show a durable dismissible notice. Never reset on corruption or an unknown newer schema. Keep the SQLite migration ledger. Branding changes must not reset, silently relocate, or rename existing learner roots.

## Build, install and surfaces

Use supported Node/pnpm ranges from `package.json` and `toolchain.json`; `.node-version` and the recorded package-manager version are bootstrap recommendations. `make setup` installs development dependencies; `make setup build` installs the source-build closure. `make help` (or `make h`) lists grouped commands and shortcuts: `d` for dev, `b` for build, `l` for logs, and `make kill` stops desktop processes plus local Android emulators. `make folder` opens the repository in the system file manager; group help (`make verify`, `make package`) lists specialized commands. Use `make build workspace` only for all surfaces. `development.json` holds optional executable overrides, not task bookkeeping.

Desktop main, preload and renderer have separate bundles. The desktop build owns the MCP server build prerequisite; packaging builds desktop first, then stages the MCP helper with `--skip-build` to reuse that output. Standalone helper generation still builds the server by default. Inspect `apps/desktop/electron-builder.yml` and `scripts/build/build-mcp-helper.mjs` before changing packaged resources; keep immutable curriculum and helper resources separate from learner storage. Use `make package inspect` for footprint budgets. `make clean` owns generated output, not learner records, dependencies or installer state.

Installers in `install/` own per-user installation inventories, launchers and activity links. Updates use an explicit fast-forward source update and build before replacement; they refuse running apps and preserve unknown/modified files. Uninstall keeps learner data by default; destructive options require established ownership and the installer's confirmation. Never work around an operation lock by guessing process ownership. Development and installed configuration are separate; existing learner folders are selected explicitly and opened in place.

The website is a React/Vite landing page using shared browser controls/tokens. Its existing Vercel project also hosts the pilot account and generation API; always deploy the combined artifact. `make website dev`, `make website build` and `make website preview` own local iteration. Inspect supported locales, keyboard interaction and narrow layouts in a real browser. `scripts/build/package-hosting.mjs` and `scripts/build/package-functions.mjs` own combined static/function packaging and deployment help; unknown URLs must remain 404 and bundled font notices must remain available. The existing packaging commands are build primitives for CI. Release delivery must use manually dispatched GitHub Actions; do not generate release artifacts or publish from the maintainer’s local checkout by default. `make release` and `make deploy production` show the manual workflow instructions without uploading.

Mobile is an Expo/native, authenticated offline flashcard companion. Desktop publishes saved decks through `packages/mobile-sync`; `packages/contracts/src/mobile-sync.ts` owns the versioned snapshot boundary. Mobile caches content and mobile-only progress in Expo SQLite, independently of desktop learning progress and AI routing. `packages/learning-ui` owns shared flashcard translations; platform controls stay separate. Its `app.json` owns native configuration; do not edit generated ignored Android/iOS projects. `make mobile config` resolves configuration and `make mobile build` exports JavaScript/Hermes bundles, not verified native applications. Native launches need an actual target and the Android verification skill (iOS requires a Mac). Preserve native design exports independently from browser CSS.

## Release delivery policy

The maintainer wants to keep the monorepo and manually start CI/CD in GitHub to generate distribution builds and publish releases/deployments. Local development builds and interactive verification remain supported; release generation should not require local packaging. The implementation is `.github/workflows/build.yml` and `.github/workflows/publish.yml`, with shared Node tooling in `scripts/ci/`. Inspect main, live Actions settings and run results before claiming the route is operational; a local workflow file alone is not a successful CI run. Do not fall back to local release generation when CI is unavailable.

Use explicit manual workflow dispatch for release delivery; no push, pull-request, tag or schedule event should publish automatically. Website and API share one deployment artifact and must ship together. Release planning, skill edits, workflow implementation, enabling remote Actions, and executing a release are distinct scopes; perform only the requested operations. Keep durable operating instructions here and in the hosted/admin skills as implementation lands, rather than adding a parallel release manual.

Before implementation edits when starting from `main`, create a working branch and advance the shared version once. Read the committed root `package.json` version on `main`. Versions are `major.minor.patch`: for features or improvements, increment minor and reset patch to zero (`0.2.1` → `0.3.0`) on `feat/<version>`; for bug fixes, increment patch and preserve minor (`0.2.1` → `0.2.2`) on `bugfix/<version>`. The agent owns this bump before implementation; only an explicit user version instruction overrides it. Preserve major unless the user explicitly requests a major change, even if the work introduces breaking changes. Mixed feature-and-fix work uses the minor bump. Preserve existing uncommitted work when branching; do not reset, stash or overwrite concurrent work. If the target branch already exists, inspect it before continuing rather than replacing it. Read-only investigations do not require a branch or version bump.

Update root and all pnpm workspace package versions, `plugins/call-nina/.codex-plugin/plugin.json`, and `apps/mobile/app.json` (`expo.version`) together, then run `node scripts/diagnostics/check-versions.mjs` to confirm alignment. Continue an existing working branch at its established version; do not bump again for follow-up requests, retries, commits, or PR updates. If a pre-existing branch lacks its intended manifest bump, reconcile it without incrementing again. Build and Publish consume committed versions and never choose or mutate them. Desktop and hosting ship the same committed version; merge into `main` before publication.

Use Conventional Commit PR titles with the shared version as a suffix: `<type>(<scope>): <description> (v<version>)`, for example `fix(release): correct publication permissions (v0.2.2)`. The branch version, manifests and suffix must agree. Bugfix PR titles use type `fix`, not `bugfix`. Use the same suffix in task commit subjects and preserve the full PR title when squash-merging. GitHub-generated release notes include merged PRs but do not bump versions. Branch creation and version alignment do not authorize committing, pushing, opening PRs, merging or publishing.

Open Actions → Build (or run `make release` for both workflow URLs). `target=all|desktop|hosting` and the `build_linux`, `build_windows`, `build_macos_intel` and `build_macos_arm` checkboxes select the artifacts. Unchecked platforms are omitted from the runner matrix. Hosting-only runs ignore them; a desktop-only run must select at least one platform. Builds accept working branches and never publish.

Open Actions → Publish on `main` and enter `build_run_id` to promote existing artifacts without rebuilding. The source must be a successful manual Build run from this repository's `main`, with all four desktop artifacts plus hosting, unexpired and from the same commit. Existing successful complete Release dry runs are also accepted. The build commit must be an ancestor of the publication dispatch commit. Publish uses tooling from its dispatch commit while artifact versions, GitHub tags and deployment metadata retain the original build's version, commit and run ID. It checks source provenance and pins artifact IDs before the Production environment gate, then rechecks identity and all manifests/checksums before any publication. It prepares desktop assets, deploys combined hosting, then publishes desktop; this is not atomic across providers. No version bump or rebuild occurs. Mobile distribution and signed installers are outside these workflows.

Repository-wide static validation belongs in local `make check` when requested, or the separately dispatched Actions → Validate workflow (`.github/workflows/validate.yml`). Validate reports version, generated-source freshness, formatting, TypeScript and ESLint checks separately. Complete validation for the intended commit before release dispatch; Build and Publish do not enforce a prior Validate run. Build preflight installs only the toolchain and checks release inputs, version consistency, commit identity, and public configuration. Publish checks existing-release conflicts. Build jobs retain target-specific compilation, license/resource packaging, package inspection and artifact checksums. Named build stages report elapsed time. No automated application suites.

CI uploads checksummed artifacts with commit/run manifests for 30 days. Desktop publication creates `desktop-vX.Y.Z` and durable release assets. Inspect the run summary and downloaded native artifacts before claiming platform verification. For a failed publication, inspect GitHub/Vercel state first, then use Re-run failed jobs on the Publish run, or start Publish again with the same source build ID. Matching draft assets are verified and reused; published releases and conflicting assets/tags are never overwritten. A new Publish run may resume a matching draft for the same source build; another build ID cannot adopt that draft. Expired artifacts require a fresh build and explicit reconciliation of any old draft/tag, never automatic deletion. Only one publish run executes at a time; GitHub may replace an older pending run when more runs are queued.

## Speech runtime and curriculum assets

`packages/speech-runtime` owns device models/public curriculum audio and learner-root `speech-cache` files. These files are disposable and excluded from portable exports/mobile sync; do not add them to installer resources. Speech preferences live in SQLite migration 41. Personal Data vocabulary/learning cleanup clears the current learner’s private speech cache; shared models and curriculum downloads remain device-owned. Storage reports measured bytes separately from install estimates, and availability probes must not update cache LRU timestamps. The existing offline runtime's resumable, prefix-verified downloader and process-identity lock are shared through its `download`/`files` exports; do not change the text model catalog to install speech.

The shipped speech catalog is fail-closed: all candidates remain unqualified until runtime bundle hashes, redistribution/source obligations, four-language pronunciation/accent review and Linux execution are recorded. A runtime is shared by its engine/hash, while voice weights are installed independently. Never turn on a candidate merely because its model downloaded or its Python import succeeded. The current Lessac US-English candidate has an unresolved research-dataset license; Pocket Alba has not qualified as US English. Other candidates still need complete voice and redistribution review.

`scripts/speech/build-runtime.py ENGINE NEW_DIRECTORY` creates a self-contained CPU CPython bundle using pinned, hash-checked dependency locks, plus a regular-file checksum inventory. The manual `speech-runtime.yml` workflow prepares review artifacts only. Publish reviewed runtime binaries and corresponding required source separately, then pin their immutable URLs/checksums/file inventory in the catalog. Runtime publication is not implemented by an ordinary app build.

Build the managed-generation dependencies, then run `node scripts/speech/curriculum.mjs extract OUTPUT_DIRECTORY` to extract/deduplicate target-language text and estimate new generation cost. `generate` requires the exact reviewed digest in `NINA_SPEECH_APPROVED_DIGEST` and server-owned Google service-account JSON in `NINA_SPEECH_GOOGLE_CREDENTIALS`; it incurs paid synthesis and is a separate authorized operation. `publish` requires the same digest, reviewed generated files, and `BLOB_READ_WRITE_TOKEN`. It publishes immutable clips before the manifest. The manual `curriculum-audio.yml` workflow separates these operations. Commit only the reviewed `audio-manifest.json` into `content/curriculum/` in the later asset activation change; never commit audio. The application rejects a manifest whose raw curriculum digest differs. Course downloads use language/path IDs, not an entire language catalog.

Prepared short stories live in `content/curriculum/stories/catalog.json`, validated by `packages/contracts/src/stories.ts`. Main loads packaged content through persistence; SQLite migration 42 owns per-learner/language reading positions. Story word saves reuse vocabulary entries and curriculum provenance. Learning cleanup removes reading positions; opening/reading stories creates no proficiency evidence. Canonical curriculum localized fields require all four interface languages.
