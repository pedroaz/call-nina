# Interactive Electron verification

Give the development agent a live app it can observe, operate, and reason about one action at a time. Do not create or run automated application tests, saved scenarios, test runners, mocks, fixtures, coverage gates, or unattended checks.

This skill describes how to verify, not a requirement to launch the app after every change. Under the root exploration/refactor policy, skip or defer this loop while the app is intentionally incomplete; a broken intermediate build is not a reason to stop implementation. Report what remains unverified and run a consolidated interactive round once the refactor is integrated, before claiming working or release-ready behavior. An explicit verification request still takes precedence. When a session is run, all data, model, ownership and cleanup rules below apply.

Run commands from the repository root. Inspect `Makefile`, `scripts/dev/verify.mjs`, `scripts/dev/lib/verification-client.mjs` and `scripts/dev/lib/verification-session.mjs` for accepted action fields, limits and recovery behavior. The controller uses Playwright's Electron API without a test runner. Read the current dispatcher before constructing an unfamiliar action; do not maintain a duplicate command/API manual.

## Development loop

1. Identify the behavior changed and the smallest useful interaction. Inspect relevant redacted logs first when reproducing a bug.
2. Have the coordinator reserve the dedicated worktree at a clean commit with `verify-enter`, then run `make verify-start` there. It builds once and opens the real Electron app, using the current learner dataset and connected Codex account. For installer work, `make verify-start ARGS="--executable /absolute/app --config-dir /absolute/config"` selects the installed app and an explicit configuration directory. Startup inspection also accepts onboarding screens. Refuse conflicting/unsafe process ownership; never kill another app to obtain a session. Stop/restart after source changes so observations match the new build.
3. Use `make verify-inspect` or `make verify-shot` to observe the screen. Send a single bounded JSON action on stdin to `make verify-do`, inspect the result, and choose the next action. Do not pass JavaScript evaluation or bypass preload/IPC/persistence with database edits.
4. Before any generation, call `prepare-ai`. It selects runtime-reported `gpt-6-luna` and default reasoning on the active Codex connection through Settings, journals that connection/root and its single model preference, and verifies the saved choice. It refuses unavailable prior choices that cannot be restored through the UI; an older workload journal or changed connection/root stays unresolved instead of being guessed or discarded. If unavailable, stop that AI check and report it; do not substitute another model. Local UI checks need no generation. Do not change model preferences while exercising AI behavior.
5. Before creating an activity or saved material, call `begin-records` for its library (`material` for sources). After creation, use the opened activity/material ID from inspection and call `track`. Before editing a tracked material, capture another material baseline and track its new revision afterward. Cleanup binds records to their observed data-root generation, learning language and material revision; an unknown scope or changed revision stays blocked. Activities are removed before their unreferenced materials, with translations following the exact activity. The controller captures persisted per-language profile settings before UI mutations and restores the original target, explanations, levels/goals, enrollment, teaching profile, locale and model choices through the UI. Record other unresolved side effects with `note`; never use broad Personal Data cleanup.
6. Run `make verify-stop` when done or when the controller is busy/unresponsive. This is authorized for the exact session-owned processes without another permission request. It queues graceful UI restoration/cleanup behind the active action, waits a bounded grace period, then escalates only with recorded Linux boot/UID/PID/start-time and descendant ownership proof. It never signals a process group. Inspect cleanup separately from process exit: forced shutdown preserves original preferences, tracked records and pending-action metadata for recovery. Missing, stale or unsupported-platform ownership is a technical blocker; retain the journal and report the exact code rather than guessing a PID or removing ownership files.

Send one action as JSON on stdin, for example:

```sh
make verify-do <<'JSON'
{"action":"click","target":{"role":"button","name":"Practice"}}
JSON
```

Use accessible roles and labels from the current UI snapshot. Check the controller for other target forms. For a stopped session with unresolved recovery state, use `make verify-resume` to retain its tracked records and original preferences, then resolve them through the UI. Inspect exact record/process references and restore through the UI; never delete ambiguous records or ownership files just to unblock startup.

For a true process restart with current records, use `make verify-suspend` then `make verify-resume`: suspend retains the journal, original preferences and owned records without UI cleanup. Final `verify-stop` still restores and cleans up. Check exact process exit separately; a failed/forced suspend is retained recovery, not a successful restart check. Resume accepts `ARGS="--codex-executable /absolute/unavailable/path"` to check unavailable external Codex Voice/plugin integration without changing account authentication; do not create a fake executable. This override does not affect Nina’s app-owned standalone generation runtime and cannot establish standalone-runtime-unavailable behavior. Leave that behavior explicitly unverified unless separately observed. Resume again without the override to restore external integration discovery, and prepare Luna before further generation.

Controller preflight validates required input and exactly one target before its durable dispatch boundary. Rejected targets have private not-dispatched receipts; any failure after the boundary remains unknown. Missing historical boundary evidence is unknown too. Keep labels, fill values, prompts and raw errors out of durable evidence.

Only the authenticated coordinator may run `verify-recovery-stop`, `verify-reconcile-disclosure` and `verify-reconcile-plugin-refresh` from reviewed source, passing `ARGS="--run RUN --expected-head SHA"`; the target comes solely from that Run's existing fixed verification barrier. First attempt owned-record cleanup and settings readback through the UI, retaining any blocked obligations for supported source advancement; hand back before an older controller's stop removes identity files. The supported stop writes durable exact-process proof before unlinking ownership. The narrow offline disclosure operation requires that proof, a whole-journal fingerprint, the exact original action/time or action ID, request fingerprint, bounded historical evidence/source references and an explicit transient-effect attestation. Read the current command validator for its input contract. The separate scoped-plugin-refresh resolution additionally requires an explicit successful UI install/refresh and fresh verified plugin/MCP registration, with original and final source references. Each resolution settles only its nominated effect with dispatch occurrence unknown; it cannot waive persistent effects, missing evidence or other retained work. Receipts remain in the private journal across final stop and future sessions. Never edit the frozen checkout or journal to unblock the barrier. If retained cleanup requires corrected source, `verify-recovery-advance` accepts one bounded stdin request and advances the same stopped reserved checkout to a clean, independently reviewed descendant. It requires the expected old head/journal fingerprint, completed exact-head review and no active target worker; its prepared receipt supports retry after interrupted checkout/barrier publication. It preserves journal bytes and original-action provenance across the barrier update, then requires `verify-resume`. It never releases old cleanup obligations.

When the fixed app checkout must stay unchanged but its controller cannot resume the current journal, use the coordinator-only `make verify-recovery-inventory` and `make verify-recovery-resume` from a clean independently reviewed descendant controller checkout. Their bounded stdin contracts live in `scripts/dev/lib/verification-recovery.mjs`: bind the Run, both heads, completed released review, exact journal/failed-attempt proof digests, current complete artifact inventory and separately attested successful fixed-head launch evidence. A current artifact digest is not historical provenance. Missing output, unexplained drift, active/unreleased target ownership, overrides and pending/interrupted mutations block this path. It never builds, advances the barrier or relabels old proof.

Keep using reviewed source for recovery controls: `verify-recovery-do`, `verify-recovery-reconcile` and `verify-recovery-stop` take `ARGS="--run RUN --expected-head APP_SHA"` and resolve only the existing barrier. The resumed controller permits inspection, exact tracked-record cleanup, restoration and stop; use ordinary restoration to settle notes and settings. It does not permit generation, new records, general click/fill/select, suspension or provider experiments. App entry, Electron installation, resources and locale catalogs remain in the target; action `sourceHead` remains the app head, with separate controller/receipt provenance. After launch uncertainty, reconcile the same receipt; no command retries spawn. An intent without process ownership remains unknown, even after its launcher exits. Preserve that receipt and escalate rather than creating a replacement attempt.

Terminal proofs are archived immutably per lifecycle UUID before replacing the latest proof or removing ownership. Interrupted pointer publication/finalization reuses only that attempt's exact proof and survivor CAS; it never merges historical process lists. Keep the original failed-controller proof, current inventory and successful-launch evidence distinct. Only fresh app/controller/descendant stop proof plus completed UI cleanup permits ordinary barrier release.

An interrupted mutating request is not cancelled by a client timeout. Do not retry it or launch another app before supported stop proves process exit. On resume, successful UI restoration reconciles interrupted settings/owned-record cleanup; other interrupted actions remain explicitly unresolved. `confirm-no-creation` is limited to a persisted `begin-records` baseline, no pending/interrupted mutation or tracked record, explicit confirmation that no creation was submitted, and an unchanged live library. Missing baseline or ambiguous creation stays retained; never begin a new baseline to erase that uncertainty.

Completed session-owned exercises may retain history that blocks activity deletion. Cleanup uses exact activity, history, language and root ownership markers to delete only their exercise history through its confirmation UI before deleting the activity and then its unreferenced material; unrelated or unproven history and vocabulary stay blocked. Interrupted cleanup is settled only after scoped absence readback. Language-select reconciliation requires captured pre-dispatch target/root/initial-language ownership and successful settings restoration, retaining the original action in a resolution receipt; a historical digest without that ownership proof never authorizes a blanket select waiver.

For a historical language select that lacks pre-dispatch metadata, `restore` may receive a bounded `languageSelection` proof naming its original action/source, retained root/initial language and exact original select request. The controller accepts only the registered learning-language control labels and a cryptographic match to that receipt, then requires successful UI settings restoration; it preserves unknown dispatch occurrence and rejects mismatches. Inspect the current validator for fields, and leave the action unresolved if the original request cannot be proven.

## Evidence and failures

Plan verification after related implementation changes are integrated. On a later revision, rerun only behavior affected by the diff or changed environment; retain the original observed commit, changed scope and a specific reason earlier evidence still covers unchanged behavior. Do not claim an unobserved scenario or new-head pass. Consolidated acceptance, independent exact-head review, local `make check`, fixed-checkout ownership, settings restoration and record cleanup remain required. Reuse the supported stop/resume/recovery paths above before repeating setup or asking for manual intervention; a distinct unresolved defect goes to the coordinator. The verification agent normally uses Sol medium under assignment policy; application AI remains Luna at runtime-default effort.

Use `make logs-once ARGS="--component desktop"` with explicit filters for bounded redacted evidence. During a long action, request `status`; `VERIFY_BUSY` means the session is still executing, not permission to retry generation. Inspect the first failure before deciding whether a retry is useful.

Screenshots and visible UI snapshots may be shown in the agent session. Do not copy learner content into logs, Git, persistent trace/video archives, or reports. The screenshot is deleted on graceful stop. Native OS dialogs and external Codex Voice are outside this controller's scope.

Report the behavior actually observed, whether a real Luna generation ran, settings/record cleanup, and what remains unverified. A successful launch or source review does not establish that the changed behavior works. Do not add a saved test as a substitute for completing an interactive check.
