# Interactive Electron verification

Choose the smallest useful check. Visual evidence, behavior acceptance, process exit and cleanup completion are distinct results. Do not turn a problem in one into a blanket development blocker. No application test suites, saved journeys, fixtures, mocks or screenshot regression suites.

## Running development app (default)

Identify the running Call Nina development window, checkout/build and data root, then inspect and interact with it using available UI tools. No separate owned session, reservation, frozen checkout, Orca or historical recovery is required. Follow root `AGENTS.md` authorization: settings, drafts, active exercises and existing learner records may be changed or deleted; AI calls, development data resets and app restarts are allowed as needed for verification. No extra permission, record-ownership proof or restoration is required for this development data.

Observe the screen/accessibility tree, perform an action, then inspect the result. Verify behavior through the real UI; direct data changes may prepare/reset development state but are not evidence that a UI workflow works. Use the development skill's real-connection/model policy for AI checks. Identify exact processes before restarting the development app and leave it usable afterward. Source edits may proceed while it runs; reload/restart when needed and tie observations to the build actually inspected. Keep screenshots out of Git and diagnostic logs.

For direct controller launches, inherit the desktop session environment, including `DBUS_SESSION_BUS_ADDRESS`, `XDG_RUNTIME_DIR`, display variables, `XDG_CURRENT_DESKTOP`, `DESKTOP_SESSION` and `KDE_SESSION_VERSION` on KDE. Read these from the actual desktop shell environment; the Node tool environment may omit them. Omitting the KDE version can select the obsolete KWallet backend even when KWallet 6 is available. Diagnose storage with the real session before changing credential code; never force plaintext storage or import another application’s authentication.

If available tools cannot attach to or operate the running Electron app, report that concrete tool limitation and use a supported launch/attachment route. A tool limitation is not a policy requirement for a separate session.

## Optional repository controller session

Use this path when useful or required by the available controller tools. The commands below enforce their own reservation, process and cleanup protocol; these requirements apply only to this controller, not to direct testing in the running development app. Do not bypass controller locks or infer that its ownership restrictions prohibit authorized development data changes through other supported tools.

1. Inspect `make verify manual-status` and `make status`. Enter with `make verify manual-enter`, then follow its `make verify start` or `make verify resume` instruction. Start/resume builds the desktop before launching the real Electron app; no separate build is needed. Stopping/restarting the development app is already authorized; restart dev afterward if this controller displaced it. Entry needs no Orca or committed source.
2. The reservation binds the current chat and desktop/runtime/controller inputs. Unrelated documentation and website edits do not invalidate it. Observations apply to the source/build fingerprint captured at start. Stop your owned session before editing relevant source or rebuilding, then enter and start again. This never blocks source work: end the session first. A stopped session can enter under a new chat and current source with its compatible journal preserved. Historical observations retain their original build identity.
3. Observe with `make verify snapshot` or `make verify screenshot`. Send one bounded JSON action on stdin to `make verify do`, inspect the result, then decide the next action. For example, send `{"action":"click","target":{"role":"button","name":"Explore trail","index":0}}` or `{"action":"viewport","width":900,"height":800}` on stdin. Use the `wait` action for asynchronously loaded controls before selecting or clicking them; prefer visible accessible names or a specific summary label over a positional selector that can match hidden details. Read request validation in `scripts/dev/verify.mjs` for available actions; never inject JavaScript or edit the database to simulate user behavior. For an image input, `upload-image` accepts a discovered input `target` and an absolute local `path` to one PNG/JPEG/WebP file up to 10 MB; file bytes and paths are not retained in the journal.
4. Before live generation, run `prepare-ai`: use Nina’s real direct ChatGPT connection, GPT-6 Luna and runtime-default effort. The sole scoped exception is the selected starter-pilot model under the [hosted API and administration skill](../call-nina-hosted-admin/SKILL.md): configure the intended action's routing through Settings, open that action, then send `{"action":"prepare-ai","route":"managed"}`. This checks its visible resolved Nina/model summary against the shipped model without silently changing routing. Otherwise never substitute another model/provider. Settings baselines are recorded before mutations, and cleanup must not overwrite later user changes.
5. Before creating an activity/material, run `begin-records` with the library kind; track the ID observed after creation. Capture/track edited material revisions too. Cleanup removes only proven session-owned records through UI, including dependent session-owned history. No broad personal-data cleanup. Unknown effects stay unresolved.
   For a new word saved from a tracked flashcard deck, `begin-records` with kind `vocabulary` requires a complete library of at most 30 words. Observe the new ID in Vocabulary details, reopen its source deck/card, then `track` it: the controller proves the explicit saved-word link, since flashcard saves intentionally have learner-owned source metadata. Save one word per baseline. Cleanup removes matching review History rows before the word, using their exact evidence ownership. Removing a review from History preserves the word and its schedule; deleting the owned word afterward removes its dependent reviews. Never infer ownership from a title.
6. Finish with `make verify stop`. It restores session changes where supported, stops only exact-owned processes and releases the Manual reservation after proven exit. Cleanup failure remains a private recovery item and a failed cleanup result, not a live process claim. `make verify manual-leave` is idempotent after release. `make verify suspend` deliberately retains the reservation for a short same-session restart.

Stopping never needs another permission request for this session's exact-owned processes. Graceful shutdown is bounded; escalation requires recorded process identity, not names, groups or guessed PIDs. A timeout does not establish whether an action ran. Inspect receipts before retrying an uncertain mutation.

## Optional controller recovery and interruption

Use `make verify manual-status` to see what is blocked and the supported next action. For recovery of a stopped development Manual session, use `make verify manual-recover` with its exact reported run. It archives ownership and cleanup evidence, checks exact stop proof and releases exclusion without declaring cleanup complete. Enter the original checkout and resume with corrected source when needed. Active processes and retired orchestration ownership are never transferred by this command. Preserve their evidence and report the retained resource.

Incompatible journals can be explicitly quarantined by their reported SHA through `make verify manual-quarantine` under a recovery/cleanup request. The full original is retained privately with unresolved status; learner records and preferences are untouched. Do not translate obsolete settings by guesswork or delete uncertain records. Do not keep retrying the same rejected operation. Source work, builds and visual inspection remain available.

Restoration uses current persisted-state readback, not the permanent presence of a Save button. Already-correct settings need no write. Values different from both the original and the session's observed result are a conflict: preserve them, retain the obligation and report it. Unknown interrupted effects require evidence; do not treat a successful screenshot as proof of no mutation.

## Evidence

Inspect bounded redacted diagnostics with `make logs -- --component desktop`. Never publish learner text, prompts, credentials, raw protocols or private paths. Report changed-source checks, observed UI/behavior, live AI use, process state and pending cleanup separately. Missing behavior evidence blocks only the dependent acceptance claim; it does not prohibit unrelated authorized development.

For Electron layout checks, resize the native BrowserWindow rather than using Playwright viewport emulation. A fixed emulated viewport can survive native maximization and break both page sizing and modal backdrops. Clear any device-emulation override and verify the renderer viewport matches the native content bounds before returning the app to the user.
